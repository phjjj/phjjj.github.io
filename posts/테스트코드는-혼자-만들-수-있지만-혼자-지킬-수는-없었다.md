우리 팀에는 전담 QA 엔지니어가 없었다. 그렇다보니 많은 기능들이 한번에 출시하게 되면 QA에게 부담을 크게 주게되며 결국 병목 현상이 생겨버린다. 또한 체계적인 테스트 케이스가 없기에 QA를 진행하고 배포를했음에도 서비스 내의 주요 기능에 대한 버그가 빈번히 나타나면서 QA 단계를 거쳐도 안심할 수 없는 상황이 됐다.

그래서 나(개발자)가 도와줄 수 있는 부분이 없을까 고민했을 때, 개발단에서 테스트코드를 작성하여 주요 기능들은 배포 후 자동화로 처리할 수 있게하면 좋겠다고 떠올랐다.

## 과정
나는 프론트엔드 담당했기에, 프론트엔드에서의 테스트를 어떻게 할 지 먼저 고민했다.

최종적으로는 playwright로 하나의 페이지(서비스)대한 E2E테스트를 먼저 도입해야겠다고 결정 후 핵심 기능들에 대한 테스트를 구성하였다. 대상은 사용자 관리, 시스템 설정처럼 오랫동안 바뀌지 않은 기능부터 골랐다. 자주 바뀌는 기능부터 테스트하면 테스트를 고치는 비용이 더 클 거라 생각했기 때문이다. 그리고 Github Actions를 활용하여 배포 후 테스트가 돌아가도록 구상했다.

테스트코드는 Codegen으로 테스트 코드를 쉽게 생성할 수 있었다. 녹화한 그대로 코드가 만들어졌으니 쉽게 작성이 가능했고 부족한 부분은 AI로 보충해서 테스트코드를 완성했다.

> Codegen은 Playwright에 기본으로 들어 있는 테스트 생성기다. 브라우저에서 클릭하고 입력하면 그 동작이 테스트 코드로 기록되고, 선택자도 Playwright가 알아서 골라 준다. ([공식 문서](https://playwright.dev/docs/codegen))

Actions 스크립트도 작성했다. 배포 이후는 물론 매일 오전 8시에 테스트를 진행 후 결과 보고를 하도록 했다.

```yml
on:
  schedule:
    - cron: '17 23 * * *' # 매일 오전 8시 17분 (KST)

jobs:
  e2e:
    steps:
      - name: E2E 테스트 실행
        run: pnpm exec playwright test

      # 실패하면 스크린샷·영상·trace가 담긴 HTML 리포트를 7일간 보관
      - name: 테스트 결과 아티팩트 업로드
        if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: playwright-report
          path: playwright-report
          retention-days: 7

      - name: Slack 실패 알림
        if: failure()
        uses: slackapi/slack-github-action@v1.27.0
```

테스트를 실패할 경우 슬랙으로 알림을 보내도록 하였다. 알림의 링크를 누르면 HTML 리포트를 받을 수 있다.

이 리포트가 Actions의 아티팩트다. 아티팩트에서는 실제 테스트 흐름과 실패한 흔적을 화면으로 볼 수 있어서 원인을 찾기 편했다. E2E 테스트를 자동화한다면 꼭 추가하길 권한다.

프로젝트 중간에 백엔드 업무를 해야하는 상황이 와서 백엔드 개발에 참여했다. 프론트는 playwright로 세팅을 끝냈던 참이기에 백엔드에도 테스트 코드를 추가해야겠다고 생각이 들었고 여러 블로그 글들을 참고하였다.

그중 가장 많이 참고한 글은 [29CM QA팀의 API를 활용한 업무 효율 끌어올리기](https://medium.com/29cm/29cm-qa%ED%8C%80%EC%9D%98-api%EB%A5%BC-%ED%99%9C%EC%9A%A9%ED%95%9C-%EC%97%85%EB%AC%B4-%ED%9A%A8%EC%9C%A8-%EB%81%8C%EC%96%B4%EC%98%AC%EB%A6%AC%EA%B8%B0-3d926d7247d5)이다.

이 글은 API 테스트를 '저비용 고효율'이라고 표현한다. 그 근거는 API 스펙이 UI보다 훨씬 덜 바뀌고, 바뀌더라도 큰 폭으로 바뀌지 않아서 유지보수에 드는 리소스가 적다는 것이었다. 나도 이 점에 동의했고 동일한 방법으로 구성했다.

Postman으로 컬렉션을 만들고, Postman의 CLI 실행 도구인 Newman으로 배포 후에 돌렸다. 핵심 기능 중 변경이 적은 API를 골라 테스트를 구성했고, API마다 예상 응답값을 비교하는 검증을 넣어 통과 여부를 판단했다.

프로덕션에서는 두 테스트 모두 기존 데이터들의 대한 오염 여부가 있어 진행하지 않았고 스테이징 서버에서만 테스트가 동작하도록했다.
